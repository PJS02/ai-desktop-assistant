# 장기기억 저장 구조

`data/long_term_memory.sqlite3`의 `memories` 테이블은 자동 저장 시 한 행에 핵심 기억 한 건을
저장합니다. `text`는 사용자 발화에서 추출한 독립적인 한두 문장이고 `original_text`는
그 기억의 최초 사용자 원문입니다. AI 답변은 단기기억에만 넣습니다.
기존 발화별 기록과 `remember_dialogue()` 수동 호출은 계속 지원합니다.

| 컬럼 | 내용 |
| --- | --- |
| `id` | 기억 행의 고유 ID |
| `text` | 핵심 기억 문장. 기존 기록은 발화 원문 |
| `original_text` | 핵심 기억을 추출한 최초 사용자 원문. 기존 기록은 NULL |
| `speaker` | `user`, `assistant`, 기존 혼합 기록 `conversation`, 미지정 `unknown` |
| `importance` | LLM이 평가한 0~10 정수. 평가 기록이 없으면 NULL |
| `conversation_id` | 사용자 입력과 AI 답변을 묶는 ID. 수동·기존 기억은 NULL 가능 |
| `embedding` | 원문을 벡터화한 float32 바이너리 |
| `dimension` | 벡터 차원 수 |
| `created_at` | DB 저장 시각, UTC ISO 8601 문자열 |
| `emotional_intensity` | 캐릭터에게 감정적인 기억인 정도, 0~10. 기존 기록은 NULL |
| `recall_count` | 검색 결과로 선택된 누적 회상 횟수, 초기값 0 |
| `last_recalled_at` | 가장 최근 선택된 시각, UTC ISO 8601 문자열 |
| `strength` | 저장 또는 마지막 강화 시점의 기억 강도, 0~1. 초기값 1 |

중요도 7 이상인 새 핵심 기억만 자동 저장합니다. 반복된 같은 사실은 새 평가가 7 미만이어도
기존 기억을 보강할 수 있습니다. 중요도는 현재 사용자 입력의 평가입니다. `created_at`은 사건 발생
시각이 아니라 저장 시각입니다. 검색의 `score`는 코사인 유사도이며 중요도와 별개입니다.
임베딩 모델 이름은 `LongTermMemory.model_name` 설정으로만 관리합니다. 한 DB의
기억은 같은 모델로 벡터화해야 하며, 모델을 변경할 때는 기존 원문을 다시 임베딩해야
합니다. 차원이 다른 벡터는 검색에서 제외합니다.

## 중요도 판단 기준

LLM은 사용자 입력을 최근 대화와 검색된 장기기억 문맥에 비추어 다음 기준으로 평가합니다.

- 미래에 다시 언급될 가능성이 있는가?
- 사용자의 취향/관계/성향에 관한 정보인가?
- 중요한 사건인가?
- 약속이나 계획인가?
- 새롭게 알게 된 사실인가?
- 사용자가 명시적으로 기억해달라고 했는가?

기준의 충족 정도와 향후 대화에서의 가치를 종합해 0~10 정수를 부여합니다.
저장할 가치가 있는 정보는 7점 이상, 명시적인 기억 요청은 높은 중요도로 평가하도록
지시합니다. 인사·일시적 잡담·새로운 정보가 없는 반복은 낮게 평가합니다.
점수는 LLM의 판단이며 특정 문장에 대한 고정 점수를 보장하지 않습니다.

## 회상 우선순위

`search()`는 관련성 하한과 기억 강도 기준을 통과한 기억에 대해 `recall_score`를 계산해
높은 순으로 최대 3개를 반환합니다. 대화 시스템은 사용자 입력과 최근 대화 일부를 검색 질문으로
전달합니다. 각 항목을 0~1로 정규화하고 다음 기본 비중으로 합산합니다.

코사인 유사도가 `MIN_RECALL_SIMILARITY`(기본 0.75) 미만이면 중요도·감정 강도가 높아도
제외합니다. 기준을 통과하는 기억이 없으면 빈 목록을 반환합니다. 이 값은 실제 E5의
한국어 대화 점수 분포로 조정해야 하는 초기값이며 정확도가 검증된 절대 기준은 아닙니다.

| 기준 | 계산 | 비중 |
| --- | --- | --- |
| 현재 대화 관련성 | E5 코사인 유사도를 0~1 범위로 제한 | 40% |
| 원래 중요도 | `importance / 10` | 25% |
| 캐릭터의 감정 강도 | `emotional_intensity / 10` | 15% |
| 최근성 | 저장 후 30일마다 기여도가 절반으로 감소 | 10% |
| 회상 빈도 | `recall_count / (recall_count + 5)` | 10% |

비중은 `vector_memory.py`의 `RECALL_WEIGHTS`에서 조절합니다. 감정 강도는 저장 시
LLM이 캐릭터 성격과 현재 감정 상태를 고려해 별도로 평가합니다. 긍정·부정 여부와
관계없이 감정 반응이 강할수록 높습니다. 기존 기록에서 알 수 없는 중요도·감정 강도는
해당 항목의 가산점을 부여하지 않습니다. 해석할 수 없는 저장 시각은 최근성 0으로 둡니다.

검색 자체는 읽기 전용입니다. 정상 Gemini 응답의 `used_memory_ids` 중 이번 프롬프트에
실제로 제공한 ID만 강화하고 `recall_count`, `last_recalled_at`을 갱신합니다. 응답 실패나
메타데이터 검증 실패는 기억을 강화하지 않습니다. 모델이 사용했다고 보고한 값이므로
답변에서의 실제 활용 여부를 완벽하게 검증하는 방식은 아닙니다.
중복 사실의 재언급과 수동 `reinforce()`도 회상 횟수에 포함됩니다.
회상 빈도 보너스는 최대 10%로 제한됩니다. `score`는 원래 코사인 유사도,
`recall_score`는 기존 5개 항목의 가중합에 현재 기억 강도를 곱한 정렬 점수입니다. 회상 점수는 질문과 시간에 따라
변하므로 DB에 고정 값으로 저장하지 않습니다. 저장 중요도 7점 기준은 그대로 유지합니다.

## 기억 강화와 망각

새 기억의 강도는 1입니다. 마지막 회상 시각부터, 회상한 적이 없으면 저장 시각부터
다음 식으로 강도가 줄어듭니다.

```text
반감기(일) = 30 × (1 + importance / 10 + emotional_intensity / 10)
현재 강도 = DB에 저장된 strength × 0.5 ** (경과 일수 / 반감기)
```

중요도·감정 강도가 없으면 각 항목을 0으로 계산합니다. 반감기는 기본 30일이며
두 점수가 모두 10이면 90일입니다. 중요하고 감정적인 기억일수록 천천히 약해집니다.
저장 시각이 불명확한 기존 기억에는 임의의 시간 감쇠를 적용하지 않습니다.

- 회상 강화: 정상 응답에서 사용이 확인되거나 같은 사실이 재언급된 기억의 현재 강도에 0.20을 더합니다. 최대 1로 제한하고,
  `strength`, `last_recalled_at`, `recall_count`를 함께 저장합니다.
- 자동 망각: 현재 강도가 0.15 미만이면 자동 검색 결과에서 제외합니다.
- 회상 우선순위: 기존 5개 회상 기준 점수에 현재 강도를 곱합니다. 원래 중요도는 변경하지 않습니다.
- 데이터 보존: 망각된 기억의 원문·벡터를 DB에 계속 보관합니다. `count()`에도 포함됩니다.

감쇠는 검색·강도 조회 때 경과 시간으로 계산합니다. 앱이 꺼져 있던 기간도 반영되며
백그라운드 타이머는 필요 없습니다. 단순 조회는 DB strength를 다시 기록하지 않아
같은 기간을 중복 감쇠하지 않습니다. DB의 strength는 마지막 강화 시점의 값이므로
현재 강도를 확인하려면 `get_strength(memory_id)`를 사용하세요.

직접 관리할 때는 다음 API를 사용합니다. 모든 API는 기억 행 ID 기준입니다.

```python
memory.get_strength(memory_id)  # 현재 강도 조회, 강화하지 않음
memory.forget(memory_id)        # 강도를 0으로 만들고 검색에서 제외
memory.reinforce(memory_id)     # 직접 회상하여 +0.20 강화, 망각된 기억도 복구 가능
```

존재하지 않는 ID는 `KeyError`를 발생시킵니다. 직접 강화도 회상 횟수에 포함됩니다.
자동 검색은 현재 강도로 순위만 정합니다. 반환된 강도·`recall_score`는 검색 당시 값입니다.
같은 대화의 두 발화는 서로 독립적으로 강화·망각됩니다.

기본 반감기·강화량·망각 기준은 `vector_memory.py`의 `FORGETTING_HALF_LIFE_DAYS`,
`REINFORCEMENT_BOOST`, `FORGETTING_THRESHOLD`에서 조절합니다.

## 핵심 기억 추출과 중복 병합

Gemini가 답변·중요도·감정 강도와 함께 다음 필드를 반환합니다. 별도 LLM 요청은 추가하지 않습니다.

- `used_memory_ids`: 답변을 만드는 데 참고한 제공 기억의 ID. 없으면 빈 목록.
- `memory_summary`: 현재 사용자 입력에서 추출한 핵심 사실. 질문·인사뿐이면 빈 문자열.
- `duplicate_memory_id`: 제공된 기억 중 같은 사실인 기억의 ID. 없으면 0.

`parse_dialogue_response()`가 응답과 필드 타입·범위를 검증합니다. 정상 답변만 단기기억에
기록하고, `apply_dialogue_memory()`가 장기기억 변경을 처리합니다. AI 답변이나 문맥에서
추측한 내용을 사용자 사실로 추출하지 않도록 지시합니다.

예를 들어 “나는 바나나를 좋아해. 중요한 사실이니까 기억해”는
“사용자는 바나나를 좋아한다”로 추출합니다. 핵심 문장을 임베딩하고 원문은 별도 보존합니다.

`remember_fact()`는 다음 순서로 처리합니다.

1. 공백을 정리한 핵심 문장이 기존 사용자·혼합 기록과 정확히 같으면 같은 ID를 재사용합니다.
   이 비교는 망각된 행도 포함합니다. 사용자가 같은 사실을 다시 말하면 복구할 수 있습니다.
2. 표현이 달라도 LLM이 제공된 기억과 동일한 사실로 판정했고, 벡터 유사도도
   `MIN_DUPLICATE_SIMILARITY`(기본 0.90) 이상이면 같은 ID를 재사용합니다.
3. 중복이면 강도를 0.20 높이고 회상 횟수를 1 늘립니다. 중요도·감정 강도는 기존 값과
   새 평가 중 큰 값을 유지합니다. 최초 원문·벡터·생성 시각은 변경하지 않습니다.
4. 중복이 아니면 중요도 7 이상인 핵심 문장만 새 사용자 기억으로 저장합니다.

단순 벡터 유사도만으로는 병합하지 않습니다. “좋아한다”와 “좋아하지 않는다”, 다른 날짜의
사건, 추가 정보를 포함한 요약은 같은 기억으로 처리하지 않도록 지시합니다. 그래도 LLM의
동일 사실 판단에는 오류가 있을 수 있습니다. 이번 단계에서 모순 정보의 자동 대체는 하지 않습니다.

의미 중복의 LLM 확인 범위는 이번 프롬프트에 제공된 최대 3개 기억입니다. 범위 밖의
기억은 핵심 문장이 정확히 같은 경우만 병합합니다. 기존 DB를 일괄 요약·병합하지 않으므로
과거의 중복 행은 그대로 남습니다. 필요하면 별도 데이터 정리 작업으로 확장할 수 있습니다.
동일 ID가 답변 사용과 중복 보강에 함께 보고돼도 한 응답에서 한 번만 강화합니다.

## 기존 DB 확장과 복구

첫 로드 시 없는 컬럼을 추가하고 기존 `memory_type`, `source`, `embedding_model`
컬럼을 제거합니다. 원문·벡터·ID·저장 시각·나머지 메타데이터는 수정하지 않습니다.
초기 혼합 기록의 중요도는 알 수 없어 NULL, 발화자는 `conversation`으로 둡니다.
기존 기록을 임의로 분리하거나 재임베딩하지 않습니다. 컬럼 제거에는 SQLite 3.35 이상이 필요합니다.
기존 `remember(text)` 호출도 계속 사용할 수 있습니다.

데이터가 있는 기존 DB의 구조를 변경하기 전 SQLite backup API로
`long_term_memory.sqlite3.schema-backup-<고유 ID>` 파일을 생성합니다.
복구하려면 앱을 완전히 종료하고 현재 DB와 관련 SQLite 저널 파일을 별도 보관한 뒤,
백업 사본을 원래 DB 경로로 복원하고 이전 코드 버전으로 실행하세요.
현재 코드로 실행하면 스키마가 다시 변경됩니다. 새 코드에서 추가된 기억은 이전
백업에 없으므로 현재 DB도 함께 보관해야 합니다.
