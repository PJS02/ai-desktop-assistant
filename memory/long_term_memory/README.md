# 장기기억 저장 구조

`data/long_term_memory.sqlite3`의 `memories` 테이블은 자동 저장 시 한 행에 핵심 기억 한 건을
저장합니다. `text`는 사용자 발화에서 추출한 독립적인 한두 문장이고 `original_text`는
그 기억의 최초 사용자 원문입니다. AI 답변은 단기기억에만 넣습니다.
기존 발화별 기록과 `remember_dialogue()` 수동 호출은 계속 지원합니다.

| 컬럼 | 내용 |
| --- | --- |
| `id` | 기억 행의 고유 ID |
| `text` | 핵심 기억 문장. 기존 기록은 발화 원문 |
| `original_text` | 핵심 기억을 추출한 최초 사용자 원문. 기존 기록은 NULL |
| `speaker` | `user`, `assistant`, 기존 혼합 기록 `conversation`, 미지정 `unknown` |
| `importance` | LLM이 평가한 0~10 정수. 평가 기록이 없으면 NULL |
| `conversation_id` | 사용자 입력과 AI 답변을 묶는 ID. 수동·기존 기억은 NULL 가능 |
| `embedding` | `text`를 벡터화한 float32 바이너리 |
| `dimension` | 벡터 차원 수 |
| `created_at` | DB 저장 시각, UTC ISO 8601 문자열 |
| `emotional_intensity` | 캐릭터에게 감정적인 기억인 정도, 0~10. 기존 기록은 NULL |
| `recall_count` | 검색 결과로 선택된 누적 회상 횟수, 초기값 0 |
| `last_recalled_at` | 가장 최근 선택된 시각, UTC ISO 8601 문자열 |
| `strength` | 저장 또는 마지막 강화 시점의 기억 강도, 0~1. 초기값 1 |
| `superseded_by` | 이 기억을 대체한 기억 ID. NULL이면 대체되지 않은 기억 |
| `superseded_at` | 기억이 대체된 시각, UTC ISO 8601 문자열 |
| `memory_type` | `profile`, `temporary`, `schedule`, `event`, `unknown`. 기본 `unknown` |
| `retention_policy` | `standard` 또는 지속 정보의 명시적 보존 요청 `persistent` |
| `decay_half_life_days` | 저장 강도 구간에 적용할 반감기 스냅샷. 기존 기록의 NULL은 종전 반감기를 의미 |

중요도 7 이상인 새 핵심 기억만 자동 저장합니다. 반복된 같은 사실은 새 평가가 7 미만이어도
기존 기억을 보강할 수 있습니다. 명확한 정정으로 기존 기억을 대체하는 경우에도 7점 기준을
적용하지 않으며, 정정 기억의 중요도는 기존 기억과 새 평가 중 큰 값을 유지합니다. `created_at`은 사건 발생
시각이 아니라 저장 시각입니다. 검색의 `score`는 코사인 유사도이며 중요도와 별개입니다.
임베딩 모델 이름은 `LongTermMemory.model_name` 설정으로만 관리합니다. 한 DB의
기억은 같은 모델로 벡터화해야 하며, 모델을 변경할 때는 기존 원문을 다시 임베딩해야
합니다. 차원이 다른 벡터는 검색에서 제외합니다.

## 중요도 판단 기준

LLM은 사용자 입력을 최근 대화와 검색된 장기기억 문맥에 비추어 다음 기준으로 평가합니다.

- 미래에 다시 언급될 가능성이 있는가?
- 사용자의 취향/관계/성향에 관한 정보인가?
- 중요한 사건인가?
- 약속이나 계획인가?
- 새롭게 알게 된 사실인가?
- 사용자가 명시적으로 기억해달라고 했는가?

기준의 충족 정도와 향후 대화에서의 가치를 종합해 0~10 정수를 부여합니다.
저장할 가치가 있는 정보는 7점 이상, 명시적인 기억 요청은 높은 중요도로 평가하도록
지시합니다. 인사·일시적 잡담·새로운 정보가 없는 반복은 낮게 평가합니다.
점수는 LLM의 판단이며 특정 문장에 대한 고정 점수를 보장하지 않습니다.

## 회상 우선순위

대화 시스템은 사용자 입력과 최근 문맥의 마지막 1,000자를 검색 질문으로 전달합니다.
`search_candidates()`는 먼저 대체된 기억·수동 망각·유형별 망각 정책을 적용하고,
같은 차원의 E5 벡터를 코사인 유사도로 정렬해 기본 Top-10 후보를 반환합니다.
기본 `top_k` 모드에서는 0.75 미만도 후보가 될 수 있습니다. `threshold` 실험 모드에서는
설정된 유사도 하한으로 후보를 제외한 뒤 Top-K를 선택합니다. 전수 비교 방식은 유지합니다.

`search()`는 이 후보들의 회상 점수를 정렬해 기본 최대 3개를 반환합니다.
실제 대화에서는 같은 후보 집합을 사용해 답변용 후보 최대 3개와 추가 대조 전용 후보를 분리합니다.
한 번의 Gemini 요청에서 답변용 후보의 의미 관련성을 먼저 검증하도록 지시하고,
`relevant_memory_ids`에 보고한 기억만 답변에 사용하도록 합니다.
추가 대조 후보는 중복·정정에만 사용하도록 명시합니다. 기본값에서 LLM에 보이는 총 후보는
최대 10개이지 3개가 아닙니다. 답변용 후보 수와 전체 대조 후보 수를 혼동하지 마세요.

0.90/0.75는 검색 질문과 기억의 코사인 유사도를 이용한 중복·정정 검토 힌트입니다.
신규 요약과 동일 사실일 확률이나 최종 병합·정정의 절대 조건이 아닙니다.
검색 결과를 무관한 내용으로부터 완전히 격리하는 별도 의미 검증기는 추가하지 않았습니다.
같은 LLM이 판단·생성을 함께 하므로, ID 보고가 올바르더라도 무관한 후보의 잠재적 영향을
완전히 차단했다고 보장할 수 없습니다. 실제 E5·LLM 평가가 필요합니다.

| 기준 | 계산 | 비중 |
| --- | --- | --- |
| 현재 대화 관련성 | E5 코사인 유사도를 0~1 범위로 제한 | 40% |
| 원래 중요도 | `importance / 10` | 25% |
| 캐릭터의 감정 강도 | `emotional_intensity / 10` | 15% |
| 최근성 | 저장 후 30일마다 기여도가 절반으로 감소 | 10% |
| 회상 빈도 | `recall_count / (recall_count + 5)` | 10% |

비중은 `vector_memory.py`의 `RECALL_WEIGHTS`에서 조절합니다. 감정 강도는 저장 시
LLM이 캐릭터 성격과 현재 감정 상태를 고려해 별도로 평가합니다. 긍정·부정 여부와
관계없이 감정 반응이 강할수록 높습니다. 기존 기록에서 알 수 없는 중요도·감정 강도는
해당 항목의 가산점을 부여하지 않습니다. 해석할 수 없는 저장 시각은 최근성 0으로 둡니다.

`recall_score_mode`는 다음 두 수식을 선택합니다. 기본은 기존 기준선 `legacy`입니다.
여기서 r은 유사도를 0~1로 제한한 값, I/E는 0~10 점수, n은 강화 횟수, d는 저장 후 경과 일수입니다.
S는 일반 기억의 현재 강도이며, 보호 대상에 대해서만 검색용 최소 강도로 보정합니다.

```text
P_legacy = S * [0.40*r + 0.25*(I/10) + 0.15*(E/10) + 0.10*2^(-d/30) + 0.10*n/(n+5)]
P_strength_only = (S/0.90) * [0.40*r + 0.25*(I/10) + 0.15*(E/10) + 0.10*n/(n+5)]
```

`strength_only`는 최근성 항목을 제외하고 남은 가중치 합 0.90으로 정규화합니다.
두 모드의 실제 우열은 검증하지 않았습니다. 모드 전환은 DB 데이터를 변경하지 않습니다.

검색 자체는 읽기 전용입니다. 정상 Gemini 응답의 `used_memory_ids` 중 이번 프롬프트에
답변용으로 제공하고 관련 있다고 보고한 ID만 강화하며 `recall_count`, `last_recalled_at`을 갱신합니다. 응답 실패나
메타데이터 검증 실패는 기억을 강화하지 않습니다. 모델이 사용했다고 보고한 값이므로
답변에서의 실제 활용 여부를 완벽하게 검증하는 방식은 아닙니다.
답변용 후보 밖의 ID를 답변 근거로 보고하거나, 전체 후보 밖의 ID를 수정 대상으로 보고하면
대화 처리부는 해당 응답을 거부하고 기억을 갱신하지 않습니다. 이 검사는 출처·권한 검증이지 의미 검증이 아닙니다.
중복 사실의 재언급과 수동 `reinforce()`도 회상 횟수에 포함됩니다.
회상 빈도 보너스는 최대 10%로 제한됩니다. `score`는 원래 코사인 유사도,
`recall_score`는 선택한 수식의 가중합에 검색용 기억 강도를 반영한 정렬 점수입니다. 회상 점수는 질문과 시간에 따라
변하므로 DB에 고정 값으로 저장하지 않습니다. 정정이 아닌 새 정보의 저장 중요도 7점 기준은 그대로 유지합니다.

## 기억 강화와 망각

새 기억의 강도는 1입니다. 강화할 때까지 적용할 유효 반감기를 함께 저장합니다.
마지막 강화 시각부터, 강화한 적이 없으면 저장 시각부터 시간 감쇠를 계산합니다.

```text
H_base = 30 * (1 + importance/10 + emotional_intensity/10)
H_eff = min(H_max, H_base * (1 + beta * ln(1 + recall_count)))
현재 강도 = DB에 저장된 strength * 2 ** (-경과 일수 / decay_half_life_days)
```

기본 beta는 0.2, H_max는 180일입니다. 로그 함수는 자연로그입니다.
강화가 없는 새 기억의 기본 반감기는 30~90일이며, 반복 강화에 따라 유효 반감기가 증가합니다.
중요도·감정 강도가 없으면 각 항목을 0으로 계산합니다.
저장 시각이 불명확한 기존 기억에는 임의의 시간 감쇠를 적용하지 않습니다.

- 회상 강화: 강화 전 구간의 반감기로 현재 강도를 계산한 다음 0.20을 더하고 최대 1로 제한합니다.
  그 뒤 `recall_count`를 1 늘리고 `last_recalled_at`을 갱신합니다.
  증가한 횟수와 최신 평가로 다음 구간의 `decay_half_life_days`를 계산해 함께 저장합니다.
- 자동 망각: `temporary`, `event`, `unknown`, 현재의 `schedule`은 강도 0.15 미만이면 검색에서 제외합니다.
  `profile` 또는 명시적으로 지속 보존하는 정보에는 아래 예외 정책을 적용합니다.
- 회상 우선순위: 선택한 회상 수식에 검색용 강도를 반영합니다. 검색 자체는 원래 중요도를 변경하지 않습니다.
- 데이터 보존: 망각된 기억의 원문·벡터를 DB에 계속 보관합니다. `count()`에도 포함됩니다.

감쇠는 검색·강도 조회 때 경과 시간으로 계산합니다. 앱이 꺼져 있던 기간도 반영되며
백그라운드 타이머는 필요 없습니다. 단순 조회는 DB strength를 다시 기록하지 않아
같은 기간을 중복 감쇠하지 않습니다. DB의 strength는 마지막 강화 시점의 값이므로
현재 강도를 확인하려면 `get_strength(memory_id)`를 사용하세요.

### 반감기 변경의 소급 적용 방지

`strength`는 마지막 저장·강화 시점의 강도라는 의미를 유지합니다.
`decay_half_life_days`는 그 시점부터 이어지는 구간의 반감기 스냅샷입니다.
beta·H_max 변경이나 중복 재평가로 중요도가 높아져도 이미 경과한 구간을 새 반감기로 다시 계산하지 않습니다.
새 설정은 신규 기억 또는 다음 강화 이후 구간에 적용됩니다.

기존 DB에 추가된 스냅샷의 NULL은 기존 H_base로 시작한 구간이라는 뜻입니다.
기존 recall_count가 높더라도 다음 강화 전까지는 종전 반감기로 감쇠하고, 다음 구간부터 증가한 횟수를 반영합니다.
기존 strength·원문·생성 시각·마지막 강화 시각·회상 횟수는 마이그레이션에서 수정하지 않습니다.

### 유형별 보존과 수동 망각

`profile`은 생일·직업·지속적 취향처럼 오래 유지되는 사용자 정보입니다.
추출 시 지속성이 불확실하면 `unknown`/`standard`를 사용하도록 지시합니다.
사용자가 지속 정보를 명시적으로 기억해 달라고 요청한 경우 `retention_policy='persistent'`를 사용할 수 있습니다.
`temporary`, `schedule`, `event`에는 persistent를 허용하지 않습니다.

보호 대상은 경과 시간만으로 검색에서 제외하지 않습니다. 검색 점수에만
`S_search = max(S_actual, 0.15)`를 적용합니다. 검색 결과의 `strength`는 실제 감쇠 강도,
`search_strength`는 검색용 보정 강도입니다. 보정값을 DB strength에 쓰지는 않습니다.
수동 forget으로 DB strength가 0인 기억은 보호 대상도 검색에서 제외하며 최소 강도 보정을 적용하지 않습니다.

`schedule`은 별도 유형으로 구분하지만 이번에는 일반 감쇠·제외 정책을 유지합니다.
일정 완료·취소·만료 판정과 관련 필드는 아직 추가하지 않았습니다.

직접 관리할 때는 다음 API를 사용합니다. 모든 API는 기억 행 ID 기준입니다.

```python
memory.get_strength(memory_id)  # 현재 강도 조회, 강화하지 않음
memory.forget(memory_id)        # 강도를 0으로 만들고 검색에서 제외
memory.reinforce(memory_id)     # 직접 회상하여 +0.20 강화, 망각된 기억도 복구 가능
```

존재하지 않는 ID는 `KeyError`를 발생시킵니다. 직접 강화도 회상 횟수에 포함됩니다.
다른 기억으로 대체된 과거 기억을 강화하려 하면 `ValueError`가 발생하며 현재 사실로 되살리지 않습니다.
자동 검색은 현재 강도로 순위만 정합니다. 반환된 강도·`recall_score`는 검색 당시 값입니다.
같은 대화의 두 발화는 서로 독립적으로 강화·망각됩니다.

기본 반감기·강화량·망각 기준은 `vector_memory.py`의 `FORGETTING_HALF_LIFE_DAYS`,
`REINFORCEMENT_BOOST`, `FORGETTING_THRESHOLD`에서 조절합니다.

## 핵심 기억 추출과 중복 병합

Gemini가 답변·중요도·감정 강도와 함께 다음 필드를 반환합니다. 별도 LLM 요청은 추가하지 않습니다.

- `used_memory_ids`: 답변을 만드는 데 참고한 제공 기억의 ID. 없으면 빈 목록.
- `memory_summary`: 현재 사용자 입력에서 추출한 핵심 사실. 질문·인사뿐이면 빈 문자열.
- `duplicate_memory_id`: 제공된 기억 중 같은 사실인 기억의 ID. 없으면 0.
- `superseded_memory_ids`: 명확하게 수정·철회된 제공 사용자 기억의 ID 목록. 없으면 빈 목록.
- `relevant_memory_ids`: 답변용 후보 중 현재 질문과 관련 있다고 검증한 ID. 최대 3개.
- `memory_type`, `retention_policy`: 같은 호출에서 판단한 기억 유형·보존 정책.

`parse_dialogue_response()`가 응답과 필드 타입·범위를 검증합니다. 정상 답변만 단기기억에
기록하고, `apply_dialogue_memory()`가 장기기억 변경을 처리합니다. AI 답변이나 문맥에서
추측한 내용을 사용자 사실로 추출하지 않도록 지시합니다.

예를 들어 “나는 바나나를 좋아해. 중요한 사실이니까 기억해”는
“사용자는 바나나를 좋아한다”로 추출합니다. 핵심 문장을 임베딩하고 원문은 별도 보존합니다.

`remember_fact()`는 다음 순서로 처리합니다.

1. 공백을 정리한 핵심 문장이 기존 사용자·혼합 기록과 정확히 같으면 같은 ID를 재사용합니다.
   이 비교는 자동 망각된 행도 포함하지만 대체된 과거 버전은 제외합니다.
   사용자가 같은 사실을 다시 말하면 자동 망각된 기억을 복구할 수 있습니다.
2. 표현이 달라도 LLM이 제공된 후보와 같은 대상·속성·시점·사실 관계라고 확인한 ID를 재사용합니다.
   유사도 0.90은 후보 검토 힌트이며, 낮은 점수라는 이유만으로 최종 확인을 거부하지 않습니다.
3. 중복이면 강도를 0.20 높이고 회상 횟수를 1 늘립니다. 중요도·감정 강도는 기존 값과
   새 평가 중 큰 값을 유지합니다. 최초 원문·벡터·생성 시각은 변경하지 않습니다.
4. 중복도 정정도 아닌 새 정보는 중요도 7 이상인 핵심 문장만 사용자 기억으로 저장합니다.

단순 벡터 유사도만으로는 병합하지 않습니다. “좋아한다”와 “좋아하지 않는다”, 다른 날짜의
사건, 추가 정보를 포함한 요약은 같은 기억으로 처리하지 않도록 지시합니다. 그래도 LLM의
동일 사실 판단에는 오류가 있을 수 있습니다. 명확한 정정은 아래의 별도 대체 규칙으로 처리합니다.

의미 중복의 LLM 확인 범위는 이번 프롬프트에 제공된 전체 후보(기본 최대 10개)입니다. 범위 밖의
기억은 핵심 문장이 정확히 같은 경우만 병합합니다. 기존 DB를 일괄 요약·병합하지 않으므로
과거의 중복 행은 그대로 남습니다. 필요하면 별도 데이터 정리 작업으로 확장할 수 있습니다.
동일 ID가 답변 사용과 중복 보강에 함께 보고돼도 한 응답에서 한 번만 강화합니다.

## 기억 수정과 모순 처리

현재 사용자 입력이 같은 대상·속성의 현재 사실을 명확히 정정하면 Gemini가
`superseded_memory_ids`에 대체할 기억 ID를 반환합니다. 예를 들어 "커피를 좋아한다"를
"이제 커피를 좋아하지 않는다"로 수정합니다. "오늘은 커피를 마시기 싫다" 같은 일시적인
상태, 과거 회고, 다른 날짜의 사건·다른 사람의 정보, 추측은 대체하지 않도록 지시합니다.
기존 기억에 변경되지 않은 독립적인 사실이 함께 있거나 판단이 불명확해도 대체하지 않습니다.

- 이번 프롬프트에 제공한 전체 후보 중 `speaker='user'`인 현재 기억만 대체할 수 있습니다.
  AI 발화·혼합 기록은 자동 대체하지 않습니다. 제공되지 않은 ID는 무시합니다.
- 중복 병합과 정정 대체는 별개입니다. 정정할 때 `duplicate_memory_id`는 0이어야 합니다.
  새 핵심 사실이 없거나 ID 형식이 잘못되면 기억 메타데이터를 거부합니다.
- 정정의 최종 판단은 대상·속성·시점·사실 관계를 비교한 LLM의 보고를 사용합니다.
  검색 유사도 0.75는 후보 검토 힌트이며 최종 정정의 절대 조건이 아닙니다.
  이미 대체된 대상은 거부합니다. 높은 유사도만으로 관계를 만들지 않습니다.
- 새 기억 저장과 기존 행의 `superseded_by`, `superseded_at` 갱신은 한 트랜잭션입니다.
  실패하면 둘 다 되돌립니다. 대체된 과거 행의 원문·벡터·평가값·회상 횟수는 변경하지 않습니다.
- 기존 기억을 바로잡는 정보는 새 중요도가 7 미만이어도 반영합니다. 새 버전의 중요도는
  기존 값과 새 평가 중 큰 값을 유지하고, 감정 강도는 새 평가를 사용합니다.
- `search()`와 자동 중복 비교는 대체된 과거 기억을 제외합니다. `count()`에는 이력도 포함됩니다.
  대체된 ID가 `used_memory_ids`에도 들어 있어도 다시 강화하지 않습니다.
- 나중에 예전 상태로 돌아가면 과거 행을 되살리지 않고 새 버전을 만들어
  `첫 기억 → 수정 기억 → 재수정 기억`의 연결 이력을 유지합니다.

별도 LLM 호출은 추가하지 않습니다. 이전 6/7개 필드 응답도 지원합니다.
유형·보존 정책이 없는 응답은 unknown/standard, 관련 ID가 없는 구버전 응답은 used_memory_ids를
기존 모델의 암묵적인 관련성 보고로 취급합니다. 기존 응답에서도 ID 출처·권한은 검증합니다.
기존 DB의 모순을 일괄 정리하지 않으며, 과거 버전 조회·복구 UI도 이번 범위에 포함하지 않습니다.
정정 판단은 LLM에 의존하므로 오판할 수 있습니다. 원문과 이력을 남겨 검토할 수 있게 합니다.

## 기존 DB 확장과 복구

첫 로드 시 없는 컬럼을 추가하고 기존 `source`, `embedding_model`
컬럼을 제거합니다. 원문·벡터·ID·저장 시각·나머지 메타데이터는 수정하지 않습니다.
이번 확장에서는 memory_type=unknown, retention_policy=standard, decay_half_life_days=NULL을 추가합니다.
기존 기억에 임의로 유형·보호 정책·정정 관계를 부여하지 않습니다.
과거에 남아 있던 memory_type 컬럼은 이제 삭제하지 않습니다. preference 등 미지원 값은 원래 컬럼을
보존하고 조회에서만 unknown으로 해석합니다. 신규 입력의 유형·정책은 허용값을 검증합니다.
초기 혼합 기록의 중요도는 알 수 없어 NULL, 발화자는 `conversation`으로 둡니다.
기존 기록을 임의로 분리하거나 재임베딩하지 않습니다. 컬럼 제거에는 SQLite 3.35 이상이 필요합니다.
기존 `remember(text)` 호출도 계속 사용할 수 있습니다.

데이터가 있는 기존 DB의 구조를 변경하기 전 SQLite backup API로
`long_term_memory.sqlite3.schema-backup-<고유 ID>` 파일을 생성합니다.
복구하려면 앱을 완전히 종료하고 현재 DB와 관련 SQLite 저널 파일을 별도 보관한 뒤,
백업 사본을 원래 DB 경로로 복원하고 이전 코드 버전으로 실행하세요.
현재 코드로 실행하면 스키마가 다시 변경됩니다. 새 코드에서 추가된 기억은 이전
백업에 없으므로 현재 DB도 함께 보관해야 합니다.
이전 코드는 대체 표시를 해석하지 못하므로, 코드만 되돌리면 과거 버전까지 회상할 수 있습니다.
이전 동작으로 복구하려면 변경 전 DB 백업과 이전 코드를 함께 사용하세요.
더 오래된 코드는 memory_type을 삭제하는 마이그레이션이 있으므로 새 DB를 이전 코드로 직접 열지 마세요.
업데이트·복원 시 앱을 종료하고 서로 다른 버전을 동시에 실행하지 마세요.

## 실험 설정

`config.json`을 편집하고 앱을 다시 시작합니다. 코드에서는 `LongTermMemory(settings=MemorySettings(...))`로
동일 설정을 주입할 수 있습니다. 파일이 없으면 기본값을 사용하고, 잘못된 설정은 조용히 무시하지 않고 오류로 보고합니다.

| 설정 | 기본값 | 의미 |
| --- | --- | --- |
| candidate_limit | 10 | 유사도 Top-K 후보 수 |
| recall_limit | 3 | 답변용 후보 수. 현재 JSON 계약상 1~3 |
| retrieval_mode | top_k | top_k 또는 threshold |
| similarity_hint | 0.75 | 정정 검토 힌트. threshold 모드에서는 검색 하한 |
| duplicate_similarity_hint | 0.90 | 중복 검토 힌트 |
| half_life_beta | 0.2 | 반복 강화에 따른 로그 증가 계수 |
| max_half_life_days | 180 | 새 감쇠 구간의 유효 반감기 상한(일) |
| recall_score_mode | legacy | legacy 또는 strength_only |

단기기억 12개 메시지·프롬프트용 문맥 4,000자, 기본 신규 저장 중요도 7, 강화량 0.20,
망각 기준·검색용 보호 강도 0.15는 유지합니다. recall_count는 강화 이벤트 횟수이며 검색 횟수가 아닙니다.

## 선행연구와 설계 범위

- [Generative Agents](https://arxiv.org/abs/2304.03442): 관련성·중요도·최근성을 조합하는 회상을 참고합니다.
- [MemoryBank](https://arxiv.org/abs/2305.10250): 시간 감쇠와 반복 회상에 따른 기억 갱신을 참고합니다.
- [Multilingual E5](https://arxiv.org/abs/2402.05672): 의미 임베딩 검색을 사용합니다.
- [Mem0](https://arxiv.org/abs/2504.19413): 유사 후보를 비교해 LLM이 기억 갱신을 판단하는 개념을 참고합니다.

여기의 Top-10/최종 3개, beta=0.2, H_max=180일, 0.15/0.75/0.90 및 점수 가중치·정규화식은
프로젝트의 설계·실험 설정입니다. 선행연구가 이 조합이나 최적 성능을 검증했다고 주장하지 않습니다.
테스트의 모의 LLM 관계 판단은 검증 경로를 검사할 뿐, 사람·날짜·모순을 실제 모델이 항상 정확하게
구별한다는 증거가 아닙니다. 실제 E5 검색 품질, LLM의 관련성·관계·유형 판정과 응답 품질은 별도 평가가 필요합니다.
